firewalld — filtrado por zonas
Teoría — qué hay realmente debajo
arquitectura
  firewall-cmd / firewall-config
            │
            ▼
        firewalld  (demonio, gestiona la política)
            │
            ▼
        nftables   (el motor real en el kernel)
            │
            ▼
     netfilter (hooks del kernel)

firewalld no es el cortafuegos: es quien administra el cortafuegos. Escribes zonas y servicios, y él traduce a reglas de nftables. Por eso nunca debes mezclar reglas manuales de nft con firewalld: la próxima recarga las borra.

El modelo de zonas

Una zona es un nivel de confianza. Cada interfaz o cada origen se asigna a una zona, y la zona define qué se permite.

Zona Comportamiento por defecto Uso típico
drop Descarta todo sin responder Interfaz hostil / lista negra
block Rechaza con mensaje ICMP Bloqueo explícito
public Sólo servicios explícitamente abiertos Por defecto en Rocky 9
internal / work Confianza media Red corporativa
trusted Acepta todo Casi nunca — es un agujero
⏳ El error que todos cometen: runtime vs. permanent

Sin --permanent, el cambio vive sólo hasta la próxima recarga o reinicio. Con --permanent, se guarda pero no aplica hasta un --reload. La regla práctica: prueba en runtime, y cuando funcione ejecuta firewall-cmd --runtime-to-permanent.

Lab — Rich rules y rate limit
firewalld — contener la fuerza bruta

Las rich rules permiten condiciones que una zona simple no expresa: origen, límite de tasa, registro y acción, todo en una sola regla.

bash — limitar intentos de SSH
# Máximo 3 conexiones nuevas por minuto por origen
firewall-cmd --permanent --zone=admin --add-rich-rule='
  rule service name="ssh" accept limit value="3/m"'

# Registrar los intentos, con límite para no inundar el log
firewall-cmd --permanent --zone=admin --add-rich-rule='
  rule service name="ssh" log prefix="SSH-INTENTO " level="notice" limit value="5/m" accept'

firewall-cmd --reload
firewall-cmd --zone=admin --list-rich-rules
bash — probarlo desde el cliente
# Lanza 10 conexiones seguidas: las últimas deben caer
for i in $(seq 1 10); do
    timeout 3 ssh -o BatchMode=yes noexiste@192.168.100.10 true
    echo "intento $i -> $?"
done

# En el SERVIDOR, ver los registros generados
journalctl -k --since "5 min ago" | grep "SSH-INTENTO"

Registrar todo lo denegado

bash
firewall-cmd --set-log-denied=all
firewall-cmd --get-log-denied

# Escanea desde el cliente y observa aquí
journalctl -kf | grep -i 'REJECT\|DROP'
📊 Esto es A.8.15 y A.8.16 otra vez

Un firewall que bloquea pero no registra te deja sin saber si te están atacando. --set-log-denied convierte al cortafuegos en una fuente de detección, no sólo de prevención. Correlaciónalo con lo de ayer.

SELinux — control de acceso obligatorio
Teoría — la contención dentro del kernel
DAC (permisos clásicos) MAC (SELinux)
Quién decide El dueño del archivo La política del sistema
Base de la decisión UID y GID Contexto del proceso y del objeto
¿root lo evade? Sí, siempre No: root también está sujeto
Protege contra Errores de permisos Procesos comprometidos

Un proceso confinado sólo puede hacer lo que su dominio permite, aunque corra como root. Si explotan Apache, el atacante queda atrapado en el dominio httpd_t: no puede leer /etc/shadow, ni escribir fuera de sus rutas, ni abrir puertos arbitrarios.

El contexto

formato
system_u : object_r : httpd_sys_content_t : s0
  │          │            │                   │
usuario     rol         TIPO               nivel MLS
                    (lo que importa
                     en el 99% de los casos)
🎯 Modo targeted

Es el de Rocky 9 por defecto: sólo confina los servicios de red, no los procesos de usuario. Cubre exactamente lo que está expuesto.

📋 Los tres modos

Enforcing aplica y registra · Permissive sólo registra (útil para diagnosticar) · Disabled no hace nada y exige reinicio para volver.

🚫 La regla de oro: setenforce 0 no es una solución

Es la respuesta más común en foros y la peor de todas: apaga el control que estaba haciendo su trabajo. Si algo no funciona, el problema es una etiqueta o un boolean — y hoy aprendes a encontrarlo en dos minutos. En el reto de Lynis, desactivar SELinux descalifica.

Booleans: interruptores de la política

bash
# Ver los booleans de httpd y su estado
getsebool -a | grep httpd

# Descripción legible de cada uno
semanage boolean -l | grep httpd_can_network_connect

# Activar de forma PERMANENTE (-P; sin él se pierde al reiniciar)
setsebool -P httpd_can_network_connect on
getsebool httpd_can_network_connect
💡 Antes de escribir una política, busca el boolean

La mayoría de los casos reales — que Apache se conecte a una base de datos, que use NFS, que envíe correo — ya están previstos como boolean. Escribir un módulo propio es el último recurso, no el primero.

Lab — Troubleshooting real
SELinux — mover el DocumentRoot y arreglarlo

Este es el caso clásico y el que más tiempo hace perder en producción. Vamos a provocarlo a propósito y resolverlo con método.

bash — 1. provocar el fallo
mkdir -p /web/sitio
echo "<h1>Diplomado</h1>" > /web/sitio/index.html
chown -R apache:apache /web
chmod -R 755 /web

sed -i 's|^DocumentRoot.*|DocumentRoot "/web/sitio"|' /etc/httpd/conf/httpd.conf
systemctl restart httpd

curl -I http://localhost/     # 403 Forbidden
# Los permisos DAC son correctos... y aun así falla.
bash — 2. diagnosticar (aquí se usa lo de ayer)
# Buscar las denegaciones recientes
ausearch -m AVC -ts recent -i

# Explicación legible de POR QUÉ se denegó
ausearch -m AVC -ts recent | audit2why

# Análisis completo con sugerencias
sealert -a /var/log/audit/audit.log | head -40

# Comparar etiquetas: la ruta nueva vs. la correcta
ls -Zd /web/sitio /var/www/html
bash — 3. la solución CORRECTA
# Declarar la regla de etiquetado (permanente)
semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"

# Aplicarla a lo que ya existe
restorecon -Rv /web

ls -Z /web/sitio
curl -I http://localhost/     # 200 OK, con Enforcing activo
⚠️ chcon no, semanage fcontext sí

chcon cambia la etiqueta ahora, pero el próximo restorecon o relabel del sistema la revierte y el servicio vuelve a fallar — meses después, sin que nadie entienda por qué. semanage fcontext cambia la regla, no sólo la etiqueta.

Ejercicios de SELinux
SELinux — 4 ejercicios

Ejercicio 5 — Puerto no estándar

Haz que Apache escuche en el 8088. Fallará: SELinux controla qué puertos puede abrir cada dominio.

bash
sed -i 's/^Listen 80/Listen 8088/' /etc/httpd/conf/httpd.conf
systemctl restart httpd      # falla
journalctl -xeu httpd | tail -20

# Ver qué puertos tiene permitidos el tipo http_port_t
semanage port -l | grep -w http_port_t

# Autorizar el nuevo
semanage port -a -t http_port_t -p tcp 8088
systemctl restart httpd      # ahora sí

# Y no olvides el firewall: son DOS controles distintos
firewall-cmd --permanent --zone=public --add-port=8088/tcp
firewall-cmd --reload

La lección: firewalld y SELinux son capas independientes. Abrir una no abre la otra.

Ejercicio 6 — SELinux conteniendo un ataque

Simula un Apache comprometido y comprueba la contención:

bash
# Ejecutar un comando DENTRO del dominio de httpd
runcon -t httpd_t cat /etc/shadow
# Permiso denegado, aunque lo lances como root

ausearch -m AVC -ts recent -i | tail

# Compara: como root SIN confinar, sí puede
cat /etc/shadow | head -2

Lynis — medir el hardening
🏆 Evaluación — la fase Check del ciclo PDCA

Lynis recorre cientos de comprobaciones sobre el sistema real y devuelve un hardening index de 0 a 100, más una lista priorizada de sugerencias. Es la auditoría técnica automatizada que cierra el ciclo.

Qué revisa Ejemplos que ya trabajaste
Autenticación pwquality, faillock, caducidad de contraseñas
SSH PermitRootLogin, MaxAuthTries, banner
Registro y auditoría auditd activo, psacct, retención de logs
Cortafuegos firewalld activo con política restrictiva
Hardening del kernel parámetros sysctl
Sistemas de archivos opciones nodev,nosuid,noexec
Frameworks SELinux en Enforcing
Malware y parches escáner presente, actualizaciones pendientes
📏 Los límites del número

El índice mide cobertura de comprobaciones, no seguridad real. Un servidor con 90 puntos y una contraseña de base de datos en un repositorio público está comprometido igual. Úsalo como termómetro, no como certificado.

📐 La alternativa formal

Para una auditoría ISO real se usa oscap con el perfil CIS del SCAP Security Guide, que emite un reporte trazable control por control. Lynis es más ágil para el ciclo diario de mejora.

Checkpoint final
Cierre de la sesión

Configuraste Apache en el puerto 8088 y abriste el 8088 en firewalld, pero el servicio no arranca. journalctl muestra un error al abrir el socket. ¿Qué pasa?

A El firewall no aplicó el cambio: falta --reload
B SELinux no permite a httpd_t abrir ese puerto: falta semanage port -a -t http_port_t -p tcp 8088
C Hay que poner SELinux en Permissive para que Apache funcione
D Los permisos DAC del DocumentRoot están mal
💡 Por qué

Son dos controles independientes sobre el mismo puerto: firewalld decide si el tráfico llega, SELinux decide si el proceso puede escuchar. Abrir uno no abre el otro — y la respuesta correcta nunca es apagar SELinux.
