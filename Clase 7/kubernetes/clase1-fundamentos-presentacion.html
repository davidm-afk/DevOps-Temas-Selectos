¿Para qué sirve cada cosa? En palabras simples
🏢 Imagina que Kubernetes es un edificio de oficinas donde trabajan muchas empresas.

📦 Namespace

El piso de cada empresa. Lo de un piso no se revuelve con lo de otro.

🧱 Pod

Una oficina dentro del piso. Ahí trabajan uno o más empleados (contenedores) que comparten escritorio y teléfono.

⚙️ ConfigMap

El manual pegado en la pared: "abrimos a las 9, idioma español". Cambias el manual, no al empleado.

🔑 Secret

La caja fuerte con contraseñas y llaves. Solo la abre quien tiene permiso.

🪪 ServiceAccount

El gafete del empleado: dice quién es y a qué puertas puede entrar (RBAC).

🚀 Deployment

El gerente: "quiero 3 empleados siempre". Si uno falta, contrata otro; si cambias el uniforme, los cambia uno por uno.

🌐 Service

La recepción con un número fijo. Tú llamas a recepción y ella te pasa con quien esté libre.

🏷️ Labels

Las etiquetas del gafete ("área: ventas"). Así el gerente y la recepción saben quién es de su equipo.

01

Namespace

Aislamiento lógico dentro del cluster

¿Qué es un Namespace? 01-namespace/
🏢 El cluster es un edificio; los Namespaces son los pisos. Cada equipo trabaja en el suyo sin pisar a los demás.

Reglas clave

  • Separa por entorno (dev, prod) o por equipo
  • Los nombres son únicos dentro del namespace — puede existir backend en dev y en prod
  • Ya existen: default, kube-system, kube-flannel
  • Borrar un namespace borra todo lo que contiene
# namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: bootcamp
  labels:
    env: training
    team: devops

# Aplicar y verificar
kubectl apply -f 01-namespace/namespace.yaml
kubectl describe namespace bootcamp
kubectl config view --minify | grep namespace
▶ Ejercicio · alumnos
Imperativo vs. declarativo
# Imperativo: "haz esto"
kubectl create namespace dev
kubectl create namespace dev
Error: namespaces "dev" already exists
# Declarativo: "así debe quedar"
kubectl apply -f namespace.yaml
kubectl apply -f namespace.yaml
namespace/bootcamp unchanged
apply es idempotente: lo puedes correr N veces y el resultado es el mismo. Por eso es la base de la automatización (y de GitOps en la Clase 4).

Limpieza: kubectl delete namespace dev prod

02

Pod

La unidad mínima de despliegue

Anatomía de un Pod 02-pod/01-pod-basico.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-nginx
  labels:              # ← los usará el Service
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80  # informativo
      resources:
        requests: { cpu: "100m", memory: "64Mi" }
        limits:   { cpu: "200m", memory: "128Mi" }

🧱 Qué es

  • Uno o más contenedores que comparten IP, red (localhost) y volúmenes
  • IP propia de la red de Flannel (10.244.x.x)
  • Efímero: si muere, no regresa solo

👀 Señalar en el YAML

  • requests = lo que reserva el scheduler · limits = el techo
  • containerPort no abre nada por sí solo
  • labels: el "pegamento" de Kubernetes

Ciclo de vida: Pending → Running → Succeeded / Failed

▶ Demo en vivo · instructor
Crear, inspeccionar y entrar al Pod
kubectl apply -f 02-pod/01-pod-basico.yaml
kubectl get pods --watch

# ¿En qué worker quedó? ¿Qué IP tiene?
kubectl get pod pod-nginx -o wide

# Events = el historial del Pod
kubectl describe pod pod-nginx
kubectl logs pod-nginx
# Entrar al contenedor
kubectl exec -it pod-nginx -- bash
  nginx -v
  exit

# Acceder sin Service (solo depuración)
kubectl port-forward pod/pod-nginx 8080:80 &
curl http://localhost:8080
kill %1
❓ ¿Quién eligió el worker? El Scheduler del Control Plane, con base en los requests y los recursos libres de cada nodo.
Sidecar e Init: explicado fácil
👨‍🍳 Piensa en el Pod como la cocina de un restaurante. El contenedor principal es el chef.

⏳ Init Container = el que abre la cocina

Llega antes que el chef: prende las luces, revisa que haya gas y que llegó el pedido. Cuando termina, se va. Solo entonces entra el chef.

Si algo falla (no hay gas), el chef no entra: el Pod se queda en Init:0/1.

Ejemplos reales: esperar a que la base de datos esté lista · correr migraciones · descargar archivos · preparar permisos de una carpeta.

🤝 Sidecar = el ayudante del chef

Trabaja al mismo tiempo que el chef, en la misma cocina. No cocina el plato principal: lava, anota pedidos, saca la basura.

Comparten la misma mesa (volumen) y se hablan sin gritar (localhost). Por eso ves READY 2/2.

Ejemplos reales: enviar logs a un sistema central · proxy de red (Envoy en Istio) · recargar configuración · métricas.

Pods con más de un contenedor: Sidecar e Init

🤝 Sidecar 02-pod-multiples-contenedores

app escribe en /var/log/app.log; sidecar-log-reader hace tail -f. Comparten un volumen emptyDir.

kubectl apply -f 02-pod/02-pod-multiples-contenedores.yaml
kubectl get pods            # READY 2/2
kubectl logs pod-sidecar -c sidecar-log-reader -f
kubectl logs pod-sidecar -c app   # vacío ¿por qué?

El app no escribe en stdout: escribe al archivo. Con varios contenedores, -c es obligatorio.

⏳ Init Container 03-pod-init-container

Corre antes que los contenedores principales y debe terminar con éxito. Útil para esperar una BD, descargar config, preparar datos.

kubectl apply -f 02-pod/03-pod-init-container.yaml
kubectl get pods --watch
# Init:0/1 → PodInitializing → Running
kubectl logs pod-init -c init-esperar-servicio
kubectl describe pod pod-init | grep -A15 "Init Containers:"

Si el init falla, el Pod nunca arranca. Lo veremos de nuevo en la Clase 2 esperando a PostgreSQL.

"Guardé un archivo en el Pod… y desapareció"

Dos lecciones:
① No guardar estado en el Pod → PersistentVolumes (Clase 2)
② Nadie recreó el Pod por nosotros → Deployment (Lab 06)

Dos formas de consumir un ConfigMap 03-configmap/
12-factor app: la misma imagen corre en dev y en prod; lo único que cambia es el ConfigMap. La imagen no se toca.

① Variables de entorno 02-…-envvar

② Archivos en un volumen 03-…-volumen

volumeMounts:
  - name: config-volume

  - name: config-volume

kubectl exec pod-config-vol -- ls -la /etc/app-config/

04

Secret

Datos sensibles: contraseñas, tokens, certificados

Base64 no es cifrado 04-secret/
# Codificar (¡siempre echo -n!)
echo -n "mi-password" | base64   # bWktcGFzc3dvcmQ=

kubectl apply -f 04-secret/01-secret.yaml
kubectl describe secret db-credentials  # solo tamaños
kubectl get secret db-credentials -o yaml  # base64

# Cualquiera con acceso lo decodifica:
kubectl get secret db-credentials \
  -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
mi-password
# Al inyectarlo, Kubernetes decodifica solo
kubectl apply -f 04-secret/02-pod-con-secret.yaml
kubectl exec pod-con-secret -- env | grep DB

❓ Entonces, ¿para qué sirve?

  • RBAC: puedo dar acceso a ConfigMaps sin dar acceso a Secrets
  • Separación de responsabilidades
  • Base para cifrado real: Vault, Sealed Secrets, External Secrets Operator
Trampa típica: echo "x" | base64 sin -n codifica también el salto de línea → la contraseña "no funciona".
Un Secret en Git, aunque esté en base64, es una contraseña publicada.

Deployment

Réplicas, actualizaciones sin caída y auto-recuperación

Un supervisor para los Pods 06-deployment/01-deployment.yaml
🚀 Deployment estrategia, historial de versiones
↓
📋 ReplicaSet "que siempre haya 3"
↓
Pod-1Pod-2Pod-3
kubectl apply -f 06-deployment/01-deployment.yaml
kubectl get deploy,rs,pods -o wide   # repartidos en workers
kubectl scale deployment nginx-deployment --replicas=5

❤️ livenessProbe

¿El contenedor sigue vivo? Si falla failureThreshold veces → kubelet reinicia el contenedor.

🚦 readinessProbe

¿Puede recibir tráfico? Si falla → el Pod sale de los endpoints del Service, pero no se reinicia.

livenessProbe:
  httpGet: { path: /, port: 80 }
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3
Rolling update: actualizar sin caída
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1        # hasta 4 Pods (3+1) durante el cambio
    maxUnavailable: 1  # mínimo 2 de 3 disponibles
# Terminal 1
kubectl get pods --watch

# Terminal 2
kubectl set image deployment/nginx-deployment nginx=nginx:1.26
kubectl rollout status deployment/nginx-deployment
kubectl get rs           # RS nuevo con 3, RS viejo con 0
kubectl rollout history deployment/nginx-deployment
  • 1
    Se crea un ReplicaSet nuevo con la imagen nginx:1.26
  • 2
    Sube un Pod nuevo; cuando pasa la readinessProbe, se baja uno viejo
  • 3
    Se repite hasta que el RS nuevo tiene 3 y el viejo 0
  • ✓
    El RS viejo se conserva (en 0): es lo que permite el rollback
💥 Falla en vivo
Desplegar una imagen que no existe
kubectl set image deployment/nginx-deployment \
  nginx=nginx:version-no-existe
kubectl get pods --watch
nginx-deployment-xxxx   0/1   ErrImagePull
nginx-deployment-xxxx   0/1   ImagePullBackOff

# Recuperar
kubectl rollout undo deployment/nginx-deployment
kubectl rollout status deployment/nginx-deployment
kubectl describe deployment nginx-deployment | grep Image
El servicio no se cae. Los Pods nuevos nunca quedan Ready, así que el rollout se detiene y los viejos siguen atendiendo.
Con maxUnavailable: 1 se sacrifica un Pod viejo → quedan 2 de 3. En el integrador usamos maxUnavailable: 0: no se baja ninguno hasta que el nuevo esté listo.
▶ Ejercicio · alumnos
Deployment real: ConfigMap + Secret + SA
# Labs 03 + 04 + 05 juntos
kubectl apply -f 06-deployment/02-deployment-con-config.yaml
kubectl get pods -l app=webapp
POD=$(kubectl get pods -l app=webapp \
  -o jsonpath='{.items[0].metadata.name}')
kubectl exec $POD -- env | grep -E 'APP_ENV|API_KEY'

kubectl scale deployment webapp-deployment --replicas=4

# Self-healing: matar nginx dentro del contenedor
kubectl exec $POD -- nginx -s stop
kubectl get pods --watch     # RESTARTS 0 → 1
¿Qué pasó? nginx es el proceso principal: al detenerse, el contenedor termina y el kubelet lo reinicia (restartPolicy: Always). El Pod es el mismo; sube RESTARTS.
La livenessProbe actúa cuando el proceso sigue vivo pero no responde (colgado). Las dos son parte del self-healing.

Recorrido del YAML: cómo se conectan
# Deployment → spec.template.spec
serviceAccountName: mi-app-sa          # ← Lab 05
containers:
  - name: app
    image: nginx:1.25
    envFrom:
      - configMapRef: { name: mi-app-config }  # ← Lab 03
    env:
      - name: API_KEY
        valueFrom:
          secretKeyRef: { name: mi-app-secret, key: API_KEY } # ← 04
    volumeMounts:
      - name: html-content
        mountPath: /usr/share/nginx/html
volumes:
  - name: html-content
    configMap:
      name: mi-app-config
      items:                     # solo esta clave
        - { key: index.html, path: index.html }

⚙️ Un ConfigMap, dos usos

Las claves llegan como variables (envFrom) y index.html como archivo montado sobre el directorio web de nginx. La página no está en la imagen.

🏷️ El hilo son los labels

selector.matchLabels, template.labels y el selector del Service dicen app: mi-app. Si uno no coincide, se rompe la cadena.

🛡️ Zero downtime

maxSurge: 1 + maxUnavailable: 0: primero sube el nuevo, luego baja el viejo.
