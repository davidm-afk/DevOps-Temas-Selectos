De SSH a Ansible
y el salto a Kubernetes

00 · Escenario

Una VM, dos papeles

Pregunta para abrir la claseSi mañana te piden instalar httpd, crear 5 usuarios y publicar una página en 50 servidores, ¿cuántas veces escribirías el mismo comando? ¿Y si a la mitad se cae la red?
01 · Fundamentos

Cómo funcionan las llaves SSH

SSH usa criptografía asimétrica: un par de llaves matemáticamente ligadas. La privada nunca sale de tu máquina; la pública se copia a cada servidor al que quieres entrar. Al conectarte, el servidor te lanza un reto que solo puede firmar quien tenga la privada.

Paso a paso en la VM

  1. Crear el usuario que hará de “servidor remoto” y darle un nombre de host:
    root@rocky9
    # useradd ansible
# passwd ansible
# echo "127.0.0.1   nodo1" >> /etc/hosts
# getent hosts nodo1
  2. Primero sin llaves (que vean el “antes”). Aparecen dos cosas: la huella del host y la contraseña.
    root@rocky9
    # ssh ansible@nodo1
The authenticity of host 'nodo1 (127.0.0.1)' can't be established.
ED25519 key fingerprint is SHA256:....
Are you sure you want to continue connecting (yes/no)? yes
ansible@nodo1's password: ← todavía pide contraseña
$ exit
# cat ~/.ssh/known_hosts   # aquí quedó la huella del SERVIDOR
    Dos llaves distintas, no confundirknown_hosts guarda la llave del servidor (protege al cliente de un impostor / MITM). authorized_keys guarda la llave del usuario (protege al servidor de accesos no autorizados).
  3. Generar el par de llaves del nodo de control:
    root@rocky9
    # ssh-keygen -t ed25519 -C "root@control"
# Enter, Enter (sin passphrase para el lab; en producción usa passphrase + ssh-agent)
# ls -l ~/.ssh/
-rw-------. 1 root root  411 id_ed25519       ← privada 600
-rw-r--r--. 1 root root   94 id_ed25519.pub   ← pública 644
# cat ~/.ssh/id_ed25519.pub
  4. Copiar la pública al servidor y probar:
    root@rocky9
    # ssh-copy-id ansible@nodo1          # última vez que pide contraseña
# ssh ansible@nodo1                  # entra directo ✓
$ ls -ld ~/.ssh; ls -l ~/.ssh/authorized_keys
$ cat ~/.ssh/authorized_keys          # es la misma .pub de root
$ exit

    Lo que hace ssh-copy-id “a mano”: crear ~/.ssh con 700, anexar la .pub en authorized_keys con 600 (y en RHEL, contexto SELinux correcto).

  5. Ejecutar comandos remotos sin entrar a una shell interactiva:
    root@rocky9
    # ssh ansible@nodo1 'hostname; whoami; uptime'
# for h in nodo1 nodo1 nodo1; do ssh ansible@$h 'date'; done   # "50 servidores" con un for…
Falla en vivo: permisos de ~/.ssh sshd tiene StrictModes yes: si los permisos son demasiado abiertos, ignora la llave en silencio y regresa a pedir contraseña.
romper → diagnosticar → arreglar
# chmod 777 /home/ansible/.ssh
# ssh ansible@nodo1                ← vuelve a pedir contraseña (Ctrl+C)
# ssh -v ansible@nodo1 2>&1 | grep -i -E "offering|authentications"
# journalctl -u sshd -n 10 --no-pager
Authentication refused: bad ownership or modes for directory /home/ansible/.ssh
# chmod 700 /home/ansible/.ssh
# chmod 600 /home/ansible/.ssh/authorized_keys
# ssh ansible@nodo1 hostname       ← funciona otra vez
Lección: el cliente no te dice por qué falló; el log del servidor sí.
02 · Transferencia

Copiar archivos de un punto a otro

Las mismas llaves sirven para mover archivos. Tres herramientas, tres usos:

scp

Copia simple

Rápido para un archivo o carpeta. Copia todo cada vez.

rsync

Sincronización

Solo transfiere diferencias. Ideal para respaldos y despliegues repetidos.

sftp

Sesión interactiva

Navegar, put/get. Lo usan clientes gráficos (WinSCP, FileZilla).

scp: origen → destino

root@rocky9
# Local → remoto
# echo "Reporte de aves - $(date)" > /root/reporte.txt
# scp /root/reporte.txt ansible@nodo1:/home/ansible/

# Remoto → local
# scp ansible@nodo1:/etc/os-release /tmp/os-release-nodo1

# Carpeta completa (-r)
# mkdir -p /root/sitio && for i in 1 2 3; do echo "pagina $i" > /root/sitio/p$i.html; done
# scp -r /root/sitio ansible@nodo1:~
# ssh ansible@nodo1 'ls -l ~/sitio ~/reporte.txt'

rsync: solo lo que cambió

root@rocky9
# dnf install -y rsync               # debe existir en ambos extremos (aquí es la misma VM)
# rsync -avz /root/sitio/ ansible@nodo1:/home/ansible/respaldo/
# rsync -avz /root/sitio/ ansible@nodo1:/home/ansible/respaldo/   # 2a vez: no transfiere nada
# echo "nueva" > /root/sitio/p4.html
# rsync -avz /root/sitio/ ansible@nodo1:/home/ansible/respaldo/   # solo p4.html
# rm /root/sitio/p1.html
# rsync -avz --delete --dry-run /root/sitio/ ansible@nodo1:/home/ansible/respaldo/  # qué borraría
Trampa clásica: la diagonal final rsync -a /root/sitio/ destino/ copia el contenido de sitio.
rsync -a /root/sitio destino/ copia la carpeta → termina en destino/sitio/. Pruébenlo ambos y comparen con tree o ls -R.
Puente hacia Ansible“Correrlo dos veces y que la segunda no haga nada” tiene nombre: idempotencia. Es la idea central de lo que sigue.

sftp: modo interactivo

root@rocky9
# sftp ansible@nodo1
sftp> pwd ; ls
sftp> get reporte.txt /tmp/reporte-bajado.txt
sftp> put /etc/hostname
sftp> bye
03 · Motivación

¿Por qué Ansible y no un script de bash?

Primero el problema: un script “ingenuo”
configura.sh
#!/bin/bash
for h in nodo1; do
  ssh ansible@$h 'echo "zona=aves" >> ~/config.txt'
done
Ejecútenlo 3 veces y revisen ~ansible/config.txt: tres líneas repetidas. El script describe acciones, no el estado que queremos. Además: no reporta qué cambió, no maneja errores por host y hay que “saber bash” para leerlo.
⟳

Idempotente

Describes el estado deseado; si ya está así, no toca nada (ok vs changed).

⇢

Sin agente

Solo necesita SSH y Python en el nodo. Nada que instalar ni mantener en los servidores.

≡

Declarativo y legible

YAML que entiende un sysadmin, un dev o un auditor. El playbook es documentación.

▦

Inventario

Grupos de hosts (web, db, prod…). El mismo playbook sirve para 1 o 500 servidores.

⧉

Módulos

Miles de módulos: paquetes, usuarios, archivos, servicios, nubes, red, VMware, Kubernetes.

✓

Seguro de probar

--check --diff muestra qué cambiaría sin aplicarlo.

⎇

Infraestructura como código

Los playbooks van a Git: revisión, historial, rollback, CI/CD.

⇶

Paralelo

Ejecuta en varios hosts a la vez (forks, 5 por defecto).

04 · Preparación

Instalación, inventario y ansible.cfg

root@rocky9
# dnf install -y ansible-core          # viene en AppStream de Rocky 9
# ansible --version
# mkdir -p /root/devops2026/ansible && cd /root/devops2026/ansible
ansible-core vs ansibleansible-core trae el motor y la colección ansible.builtin. Módulos como ansible.posix.firewalld o community.general.* requieren instalar la colección (ansible-galaxy collection install ansible.posix). En esta clase usamos solo ansible.builtin.
inventario.ini
[web]
nodo1  ansible_host=127.0.0.1

[zoologico:children]
web

Grupos con [nombre]; grupos de grupos con :children. Siempre existe el grupo implícito all.

ansible.cfg
[defaults]
inventory   = ./inventario.ini
remote_user = ansible
forks       = 5

Ansible busca la configuración en este orden: $ANSIBLE_CONFIG → ./ansible.cfg → ~/.ansible.cfg → /etc/ansible/ansible.cfg. Por eso trabajamos dentro del directorio del proyecto.

root@rocky9

05 · Actividades básicas

Comandos ad-hoc

Sintaxis: ansible <hosts> -m <módulo> -a "<argumentos>" [-b]. Útiles para tareas rápidas y para entender los módulos antes de escribir playbooks.

  1. Conectividad. ping no es ICMP: prueba SSH + Python en el nodo.
    actividad 1
    # ansible all -m ansible.builtin.ping
nodo1 | SUCCESS => { "changed": false, "ping": "pong" }
  2. Facts. Lo que Ansible sabe del host sin que se lo digas.
    actividad 2
    # ansible nodo1 -m ansible.builtin.setup -a "filter=ansible_distribution*"
# ansible nodo1 -m ansible.builtin.setup -a "filter=ansible_memtotal_mb"
# ansible nodo1 -m ansible.builtin.command -a "df -h /"
  3. Instalar un paquete — falla primero.
    actividad 3
    # ansible web -m ansible.builtin.dnf -a "name=tree state=present"
nodo1 | FAILED! => ... "This command has to be run under the root user."
# ansible web -b -m ansible.builtin.dnf -a "name=tree state=present"
nodo1 | FAILED! => ... "Missing sudo password"
    El usuario ansible no es root ni tiene sudo. Lo arreglamos en el nodo administrado:
    root@rocky9
    # echo 'ansible ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/ansible
# chmod 0440 /etc/sudoers.d/ansible
# visudo -cf /etc/sudoers.d/ansible     # valida sintaxis: un sudoers roto te deja sin sudo
# ansible web -b -m ansible.builtin.dnf -a "name=tree state=present"
nodo1 | CHANGED => ...
# ansible web -b -m ansible.builtin.dnf -a "name=tree state=present"
nodo1 | SUCCESS => { "changed": false ... }   ← idempotencia
  4. Idempotencia: shell vs módulo. Ejecuten cada uno 3 veces y comparen el color y el archivo.
    actividad 4
    # NO idempotente: siempre CHANGED, duplica líneas
# ansible web -m ansible.builtin.shell -a "echo 'zona=aves' >> ~/notas.txt"

# Idempotente: describe el estado "esta línea existe"
# ansible web -m ansible.builtin.lineinfile -a "path=/home/ansible/notas2.txt line='zona=aves' create=true"

# ssh ansible@nodo1 'cat ~/notas.txt; echo ---; cat ~/notas2.txt'
    Regla prácticacommand/shell son el último recurso: Ansible no sabe si cambiaron algo. Si existe un módulo, úsalo.
  5. Archivos, usuarios y servicios.
    actividad 5
    # ansible web -m ansible.builtin.copy -a "src=/root/reporte.txt dest=/home/ansible/reporte-ansible.txt mode=0640"
# ansible web -b -m ansible.builtin.file -a "path=/opt/zoologico state=directory mode=0755"
# ansible web -b -m ansible.builtin.user -a "name=koala comment='Cuidador koalas'"
# ansible web -b -m ansible.builtin.user -a "name=koala state=absent remove=true"
# ansible web -b -m ansible.builtin.service -a "name=sshd state=started enabled=true"
  6. La documentación vive en la terminal.
    actividad 6
    # ansible-doc -l | wc -l
# ansible-doc ansible.builtin.user          # ir a EXAMPLES con /EXAMPLES
# ansible-doc -s ansible.builtin.lineinfile  # resumen de parámetros
06 · Automatización real

Playbooks

Un playbook es el ad-hoc convertido en código: versionable, repetible y legible.

Playbook 1 · usuarios con loop

usuarios.yml
---
- name: Cuidadores del zoológico
  hosts: web
  become: true
  vars:
    cuidadores:
      - koala
      - panda
      - lince
  tasks:
    - name: Crear grupo cuidadores
      ansible.builtin.group:
        name: cuidadores
        state: present

    - name: Crear usuarios
      ansible.builtin.user:
        name: "{{ item }}"
        groups: cuidadores
        append: true
        shell: /bin/bash
      loop: "{{ cuidadores }}"

    - name: Directorio compartido
      ansible.builtin.file:
        path: /opt/zoologico
        state: directory
        group: cuidadores
        mode: "2770"
root@rocky9
# ansible-playbook usuarios.yml --syntax-check
# ansible-playbook usuarios.yml
# ansible-playbook usuarios.yml        # PLAY RECAP → changed=0
# id panda; ls -ld /opt/zoologico
Conexión con clases anterioresEl modo 2770 es el bit SGID que vimos en permisos: los archivos creados heredan el grupo cuidadores. Ansible no inventa nada nuevo: automatiza lo que ya saben hacer.

Playbook 2 · servidor web con template y handler

web.yml
---
- name: Sitio del zoológico
  hosts: web
  become: true
  vars:
    titulo: "Zoológico DevOps 2026"
  tasks:
    - name: Instalar httpd
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Publicar index.html desde plantilla
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        owner: root
        group: root
        mode: "0644"
      notify: Reiniciar httpd

    - name: httpd iniciado y habilitado
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true

  handlers:
    - name: Reiniciar httpd
      ansible.builtin.service:
        name: httpd
        state: restarted
index.html.j2 (Jinja2)
<html>
  <body style="font-family:monospace;background:#111;color:#5af78e">
    <h1>{{ titulo }}</h1>
    <p>Servidor: {{ ansible_facts['hostname'] }}</p>
    <p>SO: {{ ansible_facts['distribution'] }} {{ ansible_facts['distribution_version'] }}</p>
    <p>Memoria: {{ ansible_facts['memtotal_mb'] }} MB</p>
    <p>Desplegado por Ansible</p>
  </body>
</html>

Secuencia de ejecución para la demo

root@rocky9
# ansible-playbook web.yml --check --diff   # 1. ¿qué haría? (no aplica nada)
# ansible-playbook web.yml                  # 2. aplica: changed + handler corre
# curl -s localhost
# ansible-playbook web.yml                  # 3. changed=0, el handler NO corre
# ansible-playbook web.yml -e "titulo='Zoológico - turno vespertino'" --diff
                                            # 4. solo cambia la plantilla → handler reinicia
# curl -s localhost
Si en la VM ya hay httpd de un lab anteriorEl playbook sobrescribe /var/www/html/index.html. Respáldenlo antes o cambien dest.
Lo que deben llevarse
  • Ansible converge el sistema al estado descrito y reporta qué cambió.
  • Handlers = reiniciar solo cuando hace falta.
  • Variables + facts + templates = un mismo playbook para muchos servidores distintos.

07 · Orquestación

¿Para qué sirve Kubernetes?

Con Podman ya saben empaquetar y correr una aplicación en un contenedor. El problema aparece cuando tienes muchos contenedores, en muchos servidores, que deben estar siempre arriba. Kubernetes es un orquestador: tú declaras qué quieres (“3 réplicas de esta imagen, expuestas en el puerto 80”) y él decide dónde y se encarga de mantenerlo así.

El puente conceptual con Ansible Ambos son declarativos: describes el estado deseado.
· Ansible lleva el sistema a ese estado cuando tú ejecutas el playbook.
· Kubernetes lo compara continuamente (ciclo de reconciliación): si algo se desvía —un pod muere, un nodo cae— lo corrige solo, sin que nadie ejecute nada.
⟲

Auto-reparación

Reinicia contenedores caídos y reprograma pods si un nodo muere.

⇅

Escalamiento

Más réplicas con un comando o automáticamente por CPU/memoria (HPA).

⇄

Descubrimiento y balanceo

Un Service da IP y nombre DNS estables frente a pods que van y vienen.

↻

Despliegues sin downtime

Rolling updates y rollback a la versión anterior.

⚙

Config y secretos

ConfigMaps y Secrets separados de la imagen.

▤

Almacenamiento

PV/PVC y StorageClass: el pod pide disco, el clúster lo provee (NFS, CSI…).

08 · Arquitectura

Componentes de un clúster

ComponenteDóndeResponsabilidadSi falla…
kube-apiserverControl planeRecibe y valida todas las peticiones; único que escribe en etcdNo puedes administrar; lo que corre sigue corriendo
etcdControl planeGuarda el estado deseado y actual del clústerSe pierde la “memoria” del clúster → respaldarlo
kube-schedulerControl planeAsigna pods a nodos según recursos, afinidad, taintsPods nuevos quedan en Pending
controller-managerControl planeBucles de reconciliación (réplicas, nodos, endpoints…)Nadie corrige desviaciones
kubeletCada nodoRecibe pods asignados y pide al runtime que los ejecute; reporta saludEl nodo pasa a NotReady
kube-proxyCada nodoTraduce Services a reglas iptables/IPVSFalla el acceso vía Service en ese nodo
Runtime (CRI)Cada nodoDescarga imágenes y corre contenedoresNo arrancan contenedores
CNI / CoreDNSAdd-onsRed entre pods de distintos nodos / resolución de nombres de ServicesPods aislados o sin DNS

Objetos básicos (lo que escribirás en YAML)

Pod

Unidad mínima: 1+ contenedores que comparten red y volúmenes. Igual que un pod de Podman.

Deployment

Mantiene N réplicas de un pod y gestiona actualizaciones.

Service

IP/DNS estable y balanceo hacia los pods (ClusterIP, NodePort, LoadBalancer).

Namespace

Separación lógica: equipos, ambientes, cuotas.

Qué pasa con kubectl create deployment web --image=nginx --replicas=3

  1. kubectl envía la petición al API server, que autentica, valida y guarda el Deployment en etcd.
  2. El controller de Deployment crea un ReplicaSet; el de ReplicaSet crea 3 objetos Pod (aún sin nodo).
  3. El scheduler ve pods sin asignar y escoge un nodo para cada uno.
  4. El kubelet de cada nodo ve “tengo un pod nuevo”, le pide al runtime descargar la imagen y arrancarlo.
  5. El kubelet reporta el estado → API server → etcd. kubectl get pods muestra Running.
09 · Comparativa

Solo contenedores (Podman/Docker) vs Kubernetes

No compiten: Kubernetes corre contenedores con imágenes OCI, las mismas que construyen con un Containerfile. La diferencia es quién los administra.

AspectoPodman / DockerKubernetes
AlcanceUn solo hostClúster de N nodos como un solo recurso
Muere el contenedorPolítica --restart o unidad systemd (en ese host)El controlador recrea el pod
Muere el servidorTodo lo de ese host se caeLos pods se reprograman en otros nodos
EscalarLanzar más contenedores a mano (y cambiar puertos)kubectl scale o HPA automático
Red / descubrimientoRedes locales del host, puertos publicadosService con IP/DNS estable + balanceo entre nodos
Actualizar versiónDetener, borrar, correr la nueva → downtimeRolling update + rollout undo
ModeloMayormente imperativo (podman run …), Compose declarativo en un hostDeclarativo con reconciliación continua
ConfiguraciónVariables de entorno, volúmenes, podman secretConfigMap, Secret
AlmacenamientoVolúmenes/bind mounts localesPV/PVC/StorageClass compartidos (NFS, CSI)
ArquitecturaDocker: daemon dockerd. Podman: sin daemon, rootless posibleControl plane + kubelet + runtime CRI (containerd/CRI-O)
ComplejidadBaja: se aprende en un díaAlta: más componentes que operar
Ideal paraDesarrollo local, apps pequeñas, un servidor, edgeProducción con alta disponibilidad, microservicios, muchos equipos
Precisión: Kubernetes ya no usa Docker como runtimeDesde Kubernetes 1.24 se retiró dockershim. Los nodos usan containerd o CRI-O. Las imágenes construidas con Docker o Podman siguen funcionando porque son OCI.

10 · Cierre

Repaso y puente a la siguiente clase

SSH

Privada se queda, pública viaja a authorized_keys. Permisos 700/600 o sshd ignora la llave.

Copiar

scp copia todo, rsync solo diferencias (cuidado con la diagonal), sftp interactivo.

Ansible

Sin agente, sobre SSH, declarativo e idempotente. Módulos antes que shell.

Kubernetes

Orquestador declarativo que reconcilia de forma continua sobre un clúster.
